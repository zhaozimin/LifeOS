# LifeOS 时间记录协议

## 核心原则

时间账记录用户主动表达的事实。AI 负责把自然语言整理成分钟级时段，但不监控、不推送、不评价；只有确定成功时才能声称“已记”。明确拒绝与结果未知是两种不同状态，后者绝不能被说成“未写入”后直接重试。

本协议只管时间账本。同一句话里的金额、收支和转账属于财务域，必须另起一笔交给 `finctl`（见 [fin-bookkeeping.md](fin-bookkeeping.md)）；`time.sqlite3` 与 `finance.sqlite3` 永不合库、永不跨库事务，两笔各自写入、各自回显。

## 1. 连接与准备

1. 运行 `python3 "<SKILL_DIR>/scripts/timectl.py" clock`，以响应的 `currentLocalMinute/currentLocalDate` 冻结本轮业务时钟，并记下 `resolvedTimezone`（服务端为时间账本冻结的实际 IANA 时区；`timezone: system` 只表示配置模式）。**不要假设或重新解析账本时区**；不得读取或使用 Agent、当前宿主机、容器、消息网关或模型上下文声明的时间来替代 clock 的返回值。
2. 失败但能 locate：按 [deployment.md](deployment.md) 回到原安装目录恢复服务，再试一次。
3. 找不到安装：读取 [deployment.md](deployment.md)，先询问是否部署，不创建临时账本，更不要因为时间账不可用就把这句话记进财务账本。
4. 每次会话首次写入前运行 `configuration`；缓存最多 30 分钟，用户改主数据后立即刷新。

`locate.installPath` 只表示 LifeOS 服务和两本账本所在位置，绝不能据此改换 timectl 路径。整个会话固定使用同一个 `<SKILL_DIR>/scripts/timectl.py`。

> `<SKILL_DIR>` 指本 Skill 目录（即包含 `scripts/timectl.py` 的那个 `lifeos` 目录）的绝对路径。Hermes 平台可用 `${HERMES_SKILL_DIR}` 展开，**其他平台该变量为空，必须先换成绝对路径**，否则命令会展开成 `/scripts/timectl.py` 而报 No such file。详见 deployment.md 的防坑清单第 7 条。

完整字段与错误体以已安装仓库 `server/domains/time/routes.py` 的 `ROUTES` 契约和领域服务为准。LifeOS 不保留 FinOS/TimeOS 时代的 `docs/api.md`——那份文档已被实测认定失实，禁止据它推断字段。

## 2. 对话流原语

日常动作必须优先落到以下高层命令；这些命令自动从本机配置取 Token，写命令还会在写入前校验真实分类、项目与声明日期。每条写命令都以 `--today <clock 返回的 currentLocalDate>` 结尾；下例中的 `2026-08-01` 是示例日期，实际执行时必须换成本轮 clock 返回的真实日期，不得原样照抄：

```bash
python3 "<SKILL_DIR>/scripts/timectl.py" clock
python3 "<SKILL_DIR>/scripts/timectl.py" switch --title "开会" --category "会议" --now \
  --today 2026-08-01
python3 "<SKILL_DIR>/scripts/timectl.py" switch --title "剪辑视频" --category "剪辑" --at 9:01 \
  --today 2026-08-01
python3 "<SKILL_DIR>/scripts/timectl.py" record --title "玩部落冲突" --category "刷手机" --start 7:23 --end 8:08 \
  --today 2026-08-01
python3 "<SKILL_DIR>/scripts/timectl.py" stop --at 8:57 \
  --today 2026-08-01
python3 "<SKILL_DIR>/scripts/timectl.py" cancel --expect-start 2026-08-01T08:17 \
  --today 2026-08-01
python3 "<SKILL_DIR>/scripts/timectl.py" segments --from 2026-07-30 --to 2026-07-31
python3 "<SKILL_DIR>/scripts/timectl.py" gaps --date 2026-07-30
python3 "<SKILL_DIR>/scripts/timectl.py" update --id SEGMENT_ID --start 2026-07-30T01:12 --end 2026-07-30T05:16 \
  --today 2026-08-01
python3 "<SKILL_DIR>/scripts/timectl.py" delete --id SEGMENT_ID --reason "用户确认误记"
```

禁止用裸 curl、execute_code 或直接读取 `server/runtime/config.json`、`connection-info.txt` 代替上述命令。禁止猜端口、Token、接口名、分类 ID 或请求字段。高层命令未覆盖的 PUT/DELETE 等少量纠错操作，才允许用 `timectl.py request <METHOD> <PATH> --payload-file <JSON 文件路径>`，且路径必须落在 `/v1/time/*`（唯一例外是只读 `GET /v1/health`）；先用文件写入工具把 JSON 落地，禁止用 heredoc、`echo` 或管道把 JSON 灌给解释器。

命令选择一律以 SKILL.md 的记录决策表为准，本表只补充每种表达的执行细节：

| 用户说 | 动作 |
|---|---|
| “接下来我要开会”“我去休息了”“开始剪视频”“我睡了”“我起来了，先去洗漱” | `switch` 一次请求闭旧开新；只说“现在”用 `--now`，说了钟点用 `--at 9:01`。回执 `seamless: true` 才算无缝。睡眠、休息、洗漱都是能命名的活动，一律走这里，**不要**先 `stop` 再开段。 |
| “我现在开始写代码”，而账本当前没有进行中活动 | 同样用 `switch`。此时回执给出 `openedWithoutPredecessor: true` 与 `precedingRecord`；若其中 `gapMinutes > 0`，`display` 上行会画成 `⚠ 未记录`，原样转达即可，这段空白自然会被用户看见。 |
| “先记到这儿”“我不记了”“今天到此为止”——用户明确停止记录 | `stop --now` 或 `stop --at 8:57`；进行中段由 timectl 按账本定位，与自然日无关。这条命令会让账本从此留空白，只在用户明确不再记录时使用。刚开段的同一分钟内就说不记了时，`--now` 会由服务端按最短一分钟规则收在起点后一分钟——那是真实发生过的活动，不要改用 `cancel` 去抹掉它。 |
| 本轮刚写错、用户立刻改口 | `cancel --expect-start <上一条回执的 boundary>`。它软删该进行中段，并在那次误开曾自动收尾前一个活动时，于同一事务内把前一个活动原地恢复为进行中（回执 `restoredPrevious`；时段 ID 与全部字段不变）。禁止用 `stop` 撤销——那会留下虚假的 1 分钟。 |
| “刚才开会开了一个半小时”“睡了大概五个小时”——只给时长不给钟点 | 先反问“几点开始的”或“到几点结束”，拿到钟点后再 `record`。禁止自己做时长加减，那与“不算日期”是同一条纪律。 |
| “上午九点到十一点在写文章” | `record --start 9:00 --end 11:00` 按用户给定起止闭合补录。 |
| “昨晚 11:18 睡的，早上 6:50 醒” | `record --start 23:18 --end 6:50`：跨零点由 timectl 判定为一条跨日记录，不要自己拆成两段，也不要自己算日期。 |
| “前天上午 9 点到 11 点开了个会”——最近 400 天内更早的自然日 | `record --days-ago 2 --start 9:00 --end 11:00`。钟点仍原样写，只补一个“几天前”，日期照样由 timectl 推定；超过 400 天必须取得明确完整日期。 |
| “1:12 入睡、5:16 醒来、刷手机到 7:23，现在看开户文件” | 先查询相关时段，生成三段最终时间线，再用一次 `reconcile` 原子更新/补录/开段。 |
| “中间刷了半小时手机” | 去向可命名就用一次 `reconcile` 原子拆段。若只说“走神半小时”且去向说不清，扣除分钟目前没有对应的高层命令参数：**先问清那半小时的去向**，能命名就拆段；用户确实说不清时如实告诉他这半小时暂时只能留在原活动里，不要为此调用 `stop`（那会把他仍在进行的活动收尾）。 |
| “今天 / 这周 X 多少时间” | 用 `segments --from --to` 取回时段自行汇总，或 `gaps --date` 看某天覆盖；只查不写。需要服务端口径的区间 KPI 时才用 `request GET "/v1/time/summary/range?from=2026-07-31&to=2026-08-01"`（两个参数都必填）。 |

## 3. 字段推断与主数据护栏

按以下顺序取值（这五级顺序与财务域同构，SKILL.md 常驻层已给出总纲，此处只补时间域细则）：

1. 用户本次明确表达。
2. `/v1/time/habits` 返回的强习惯，`share >= 0.7` 才可直接沿用。
3. 最近同类时段的稳定选择。
4. 系统默认。
5. 仍有多个合理答案时，只追问影响真实性的一个字段。

无法从用户事实和现有主数据可靠推断分类时，Agent 应在构造命令前选择现有“未归类”，不得自行新建；不要把任意新名称传给 `record` 期待它自动兜底，`record` 会在写入前拒绝无效分类。新建/修改/删除分类或项目必须先展示建议并取得明确同意，再调用 `POST /v1/time/agent/operations`，`userConfirmation` 填用户确认原话。

用户明确说“核心/非核心业务”或等价性质时，把 nature 作为硬约束传入 `--nature` 或计划中的 `expectedNature`。例如“工作但不是核心业务”只能选择 nature=`support` 的现有分类；银行开户文件优先“运营事务”，不确定才用“未归类”，禁止写入 core 的“产品设计”。

项目名与财务域只做字面对齐：用户提到项目已存在于财务账本时，建项目前提醒沿用相同名称；**不读取财务账本，也不因为对齐名称而发起任何 `/v1/fin/*` 请求**。财务操作走 finctl，两本账本永不合库。

标题与备注分工如下：

- `--title` 只回答“这段时间主要在做什么”，使用忠实、短小的活动概括，不承载整段描述；专有名词和具体对象是识别事实，“枫叶银行开户文件”不得缩成“开户文件”或改成“枫野银行”。
- 先从用户描述中提取时间、分类、项目、扣除和标签；所有未被这些结构化字段消费的有意义事实，都必须忠实写入写命令的 `--note`。界面空间是否足够、当前是否显示备注，只影响呈现，不影响完整落库。
- `--note` 不编造用户没说过的事实，不重复标题或已被其他字段完整表达的信息，也不能因为内容较长而丢弃。允许去掉口头填充词，但不得删掉用户表达的对象、条件、原因、判断或结果。
- 若没有剩余的有意义事实，省略 `--note`，不要用标题复制出一条伪备注。
- 备注里出现的金额是用户说过的话，可以照录；但**时间行的回显永远不带 `¥`**，金额的账本归属由 finctl 那一笔负责。

例如，假设 configuration 中已有 `LifeOS` 项目，用户说：“我现在开始整理 LifeOS 的周视图，重点想把左侧一天时间块改成直角矩形，右侧显示我说过的说明；如果空间不够可以在界面省略，但这段产品判断要完整保留。”应执行：

```bash
python3 "<SKILL_DIR>/scripts/timectl.py" switch \
  --title "整理周视图" \
  --category "产品设计" \
  --project "LifeOS" \
  --now \
  --note "重点想把左侧一天时间块改成直角矩形，右侧显示我说过的说明；如果空间不够可以在界面省略，但这段产品判断要完整保留。" \
  --today 2026-08-01
```

用户正在开始做这件事，所以是 `switch` 而不是 `record`；末尾的 `--today` 不能省，值换成本轮 clock 返回的真实日期。

## 4. 时间冻结与写入规则

- **用户的时间是连续的，他给出的钟点是分界线。** “9:44 弄枫叶银行资料”确定的是两件事：上一件事结束于 9:44、这件事开始于 9:44。一句话只对应一个时间值和一条 `switch --at 9:44`。禁止用工具执行时刻去收尾上一件事——那是命令跑起来的分钟，不是用户表达的事实，两者之差就是账本里那些一分钟空洞的来源（真实发生过 8 次）。
- 若上一条 **Agent 来源**记录已被收在更早的分钟，`switch` 会在同一事务内把它的结束对齐到用户说的钟点，回执给出 `alignedPrevious`（含 `endedAtWas`/`endedAtNow`/`closedGapMinutes`），`display` 上行会带“已由 09:43 对齐到 09:44”。网页手工补录或导入记录不会被隐式改写，必须先征得用户确认，再用 `update --id` 显式对齐。对齐幅度超过 5 分钟时 `switch` 同样拒绝执行并要求问清那段时间在做什么。用户明确说“那段时间不记”时才加 `--allow-gap`。
- **日期算术不属于 Agent。** 用户说出的钟点原样传给 timectl 的 `HH:MM` 参数，自然日由业务时钟推定：无参照时取不晚于业务当前分钟的最近一次该钟点（若用户报的钟点只比业务时钟快几分钟，按当前分钟收敛，不会退成前一天），`--end` 则取 `--start` 之后第一次该钟点，因此“23:18 睡到 6:50”自动成为一条从前一日跨到当日的记录。不要自己拼 `YYYY-MM-DDTHH:MM`，那是历史上把 7 月 30 日写成 7 月 29 日的直接原因。
- 补录最近 400 天内更早的自然日用 `--days-ago N`（昨天 1、前天 2），钟点仍原样写；超出该范围时 timectl 会以 `LifeOSTimeError` 硬失败，必须取得用户明确日期或从 `segments` 查到完整分钟。**不要**省略 `--days-ago` 用短钟点表达更早日期：它会按最近一次解析。
- 只有两种情况写完整分钟：`update` 与 `reconcile` 修正已存在的历史时段，以及 timectl 明确要求给出完整日期时（钟点与参照分钟相同、或推出的跨度过大而产生整日歧义）。此时日期必须来自 `segments` 查到的真实记录或用户明确说出的日期，不得由“今天减一天”这类推算得出。
- 每条写命令都必须带 `--today <clock 返回的 currentLocalDate>`，这是必填参数，漏传直接失败。timectl 会核对这个声明；不符即拒绝写入并回报真实业务日期。这道护栏专门拦截“模型以为今天是昨天”的跨日幻觉。`delete` 按 id 定位、不解析任何时间，因此刻意不接受 `--today`。
- 跨零点的活动是**一条**记录，不是两条。账本允许单条时段跨越零点，统计层按自然日拆分并保证总量守恒；自行拆成两段会制造虚假边界。
- 用户说“现在已经是 8 月 1 号”“按新的一天做”等日期纠正时，立即作废所有尚未提交的旧日期计划，重新运行 clock，重查相关窗口并重建唯一最终时间线。禁止回复“昨天的分析仍然正确”。
- 仍有两种合理日期且用户没有纠正时，只追问日期，不得猜写。
- 用户在边界前后陈述的是同一活动、同一分类和同一性质时，合并成一个连续时段；“6:50 到现在一直刷手机，接下来继续刷手机”应从 6:50 保持一个 open segment，不得在消息时刻拆成两个相邻“刷手机”。只有活动、分类、性质或用户明确要求的段落发生变化时才建新边界。
- 写入前先列出唯一的预期最终时间线；历史状态只是待修正现状，不得推翻用户本轮明确事实。
- 用户说出具体钟点时必须原样使用 `--start/--at/--end`，禁止省略后退化为工具执行时刻；只说“现在”而没有钟点时才允许显式 `--now`。
- **活动切换只用 `switch`，绝不用 `stop` 再 `record`。** 后者是两次独立请求、两次各自读取执行时刻的分钟，模型推理或工具往返一旦跨过分钟边界，账本就会留下一分钟空白；这一故障已被隔离场景复现并由回归测试锁定。`switch` 只存在一个边界值，服务端在同一事务内闭旧开新，回执的 `seamless: true` 即无缝证明。回执给出 `openedWithoutPredecessor` 时说明此前没有进行中活动：这不是无缝切换，若同时带 `warning`，必须把其中的空白分钟如实告诉用户。
- 最短 1 分钟只用于用户确认真实发生但抹秒后零长的活动。本轮误开或用户即时改口必须用 `cancel --expect-start <上一条回执的 boundary>` 软删，禁止 `stop` 成 1 分钟。`cancel` 有三道护栏：起点必须与你上一条回执一致、来源必须是 agent、写入年龄必须在 0–15 分钟窗口内；审计时间落在未来也会 fail-closed。任一不符即拒绝，此时说明它属于用户既有事实，请与用户确认后改用 `delete --id`。
- 若那次误开曾自动收尾前一个活动，`cancel` 会在同一事务内把它原地恢复成进行中，回执给出 `restoredPrevious`；时段 ID、来源、创建时间与全部字段都保持不变。判据是服务端在自动收尾时落库的因果标记，而不是时间戳邻近：用户自己 `stop` 结束的活动**不会**被撤销复活。
- 禁止为执行计划创建中间进行中段；补录闭合段直接带齐 `--start/--end`，复合时间线统一用 `reconcile`。
- `categoryName`、非空 `projectName` 必须来自 configuration；时段 source 使用 `agent`。
- 补录遇 422 `overlap`：展示最少冲突信息并提议修边，例如“9:00–11:00 与 10:30 的会议重叠，改成 9:00–10:30？”
- 进行中段超过 24 小时：与用户确认真实结束点后回填；确需覆盖更长时间，按拆段协议切成每段不超过 1440 分钟。

## 5. 复合时间线与拆段协议

用户一句话涉及两个以上时段，或同时包含纠正旧段、补录和开始新活动时：

1. 先用 segments 查询相关窗口并唯一定位旧段。
2. 在内存中生成最终时间线，核对无重叠、对象保真、category nature 匹配。
3. 用文件写入工具把计划落地成 JSON 文件（例如 `/tmp/lifeos-time-plan.json`）。**禁止用 heredoc、`echo` 或管道把 JSON 灌给解释器**：`cat ... | python3 ...` 会被安全策略判为高危并中断整次写入，正确计划也会因此完全不落库。
4. 用一次 `reconcile --plan-file /tmp/lifeos-time-plan.json --verify-from ... --verify-to ...` 提交 update/delete/create 操作并取回写后窗口，同时带上 `--today <本轮 clock 返回的日期>`。
5. 服务端明确返回 4xx 时，任一操作失败都会整体回滚；不得降级成边写边修。若收到 5xx、超时或断连，事务可能已提交，必须按结果未知处理：禁止重放计划，先用只读 `segments` 核查。

计划文件只描述最终变更，不写推理过程；其中的时间必须是完整分钟：

```json
{
  "operations": [
    {"action":"update","id":"SLEEP_ID","payload":{"title":"睡眠","categoryName":"睡眠","expectedNature":"recovery","startedAt":"2026-07-31T01:12","endedAt":"2026-07-31T05:16"}},
    {"action":"create","payload":{"title":"刷手机","categoryName":"刷手机","expectedNature":"leisure","startedAt":"2026-07-31T05:16","endedAt":"2026-07-31T07:23"}},
    {"action":"create","payload":{"title":"查看枫叶银行开户文件","categoryName":"运营事务","expectedNature":"support","startedAt":"2026-07-31T07:23"}}
  ]
}
```

只有 `reconcile` 端点本身不可用（404 或服务端不支持）时才降级为旧拆段顺序。**422 之类的业务校验失败不算“事务不可用”**：那说明计划本身有问题，应当修正计划后重新提交同一次 `reconcile`，降级只会把整体失败变成半完成。

1. 用 `update` 切短旧段。
2. `record` 补写中间可命名时段。
3. `record` 或 `switch` 补写、重开剩余时段。

三步全部成功前不得回显“已记”。任一步失败，明确说明已成功的步骤、当前半完成状态和剩余动作；下一轮优先用 gaps 与 segments 定位缺口并修复。

## 6. 回显：原样转达 display（时间行字典真源）

写命令的回执带一个 `display` 数组，它由 timeview 按落库事实拼好，就是要给用户看的成品文本。

**把 `display` 的每个元素单独一行输出，一字不增、一字不减，前后不加任何话。**

```
✓ 剪辑视频 · 09:01–10:23 · 1h22m
▶ 运营事务 · 10:23 起
```

上行是刚刚封口的那一格，下行是正敞着的那一格；位置恒定，与时间轴同构。回显不报告执行了哪条命令——`switch`、`record`、`stop` 是系统的内部概念，用户不关心账本是被哪条命令改成这样的，只关心它现在是什么样。

以下内容一律不得出现在回复里：

- **过程叙述**：跑了哪些命令、先 clock 后 switch、读了哪些配置。
- **回执翻译**：`seamless: true` 是什么意思、边界为何唯一、事务是否原子。这些是护栏给我看的证据，不是给用户看的话。
- **成功声明**：不要在 `display` 前后再补一句“已记录”“已完成”——两行本身就是记录。
- **社交收尾**：“还需要我做什么吗”“需要继续记录吗”。
- **原始 JSON 与 Token**：任何情况下都不输出。

五个状态符各自只对应一种账本状态，与命令名无关；它们由脚本产出，不必也不得由模型拼装：

| 符号 | 含义 | 位置 |
|---|---|---|
| `✓` | 已封口的时间块 | 上行 |
| `▶` | 正在进行的时间块 | 下行 |
| `⚠` | 未记录的时间块（空白） | 上行 |
| `✗` | 已撤销或已删除的时间块 | 上行 |
| `⏸` | 此后没有进行中活动 | 下行 |

**时间行永不出现 `¥`。** 这五个符号只描述时间轴的占用状态，与金额无关；账务行是另一套六符号字典，写在 [fin-bookkeeping.md](fin-bookkeeping.md)。混合句拆成两笔后，两条回执各出各行，用户一眼就能分辨哪一行来自哪本账。

三种例外：

1. **复合对账**（`reconcile`）的 `display` 会超过两行，最终时间线有几段就有几行，最后一行仍是当前那一格。照样原样输出。
2. **回执没有 `display`**（渲染降级或字段缺失）：说明脚本无法确定账本状态，此时才自己按上表拼两行，拼不出就只陈述能确定的事实，绝不编造。
3. **查询**（`segments`/`gaps`/`summary`）不是记录，没有 `display`，也不用符号；两行内只给用户所问的数字与必要口径。

失败、明确 4xx 拒绝、结果未知或半完成时同样没有 `display`：按第 9 节如实说明状态与剩余动作，不得输出任何成功形态的两行。

## 7. 温和主动细则

写后核对只看 timectl 回执，不需要再补查询。温和主动是另一件事：每次会话至多在首次成功写操作后顺带查询一次今天和昨天的 gaps，仅用于判断是否值得提一句：

- 任一空白连续不少于 120 分钟；或
- 进行中段 age 超过 6 小时；“睡眠”分类超过 12 小时。

这三个数与面板的 8 小时「可疑 · 超长未闭合」阈值（服务端 `OVERLONG_SEGMENT_MINUTES`，经 `/v1/time/configuration` 下发）**不是同一个东西，不要合并**：
这里是**事前**的一句提醒，目的是在时段还开着的时候促成收尾，所以必须比面板更早开口；
面板那条是**事后**的记录标注，标的是「这段已经长得不像话，回看时请确认」。
前者若跟到 8 小时，就永远只能在损失已经发生之后才出声。

满足时在 `display` 两行之后另起一行，至多一句，只陈述区间与时长。提醒前回顾本次对话：同一空白或同一超长段已提过则不再提；用户不回应，本会话不再提。去重只使用当前对话上下文，不写本地状态；跨会话可以再提一次。绝不主动发起对话，绝无推送。

**本次写入自身带出的空白不走这条规则**：护栏发现的空白已经由 timeview 画进 `display` 的 `⚠` 行，原样转达即可，不要再用自己的话复述一遍。

## 8. 纠错、撤销与查询

- 纠正刚才一条：先用 segments 确认唯一目标，再用 `update`；不得修改 `source`。
- 撤销：只删除最近、`source=agent`、且用户描述能与标题/时间唯一对应的一条。不能唯一定位或跨会话时，列最少候选让用户选择。
- AI 本轮明确误开的时段属于自身纠错：直接运行 `cancel`，无需用户再次确认，绝不以 stop 伪造时长。`--expect-start` 是**必填**参数，值取上一条写入回执**顶层**的 `boundary`（形如 `2026-08-01T09:01` 的纯分钟串）；不要拿 `howTimesWereResolved` 里的中文轨迹串。撤销后重开正确活动时用 `--at <同一个 boundary>`，不要用 `--now`——否则纠错来回耗掉的几分钟会被错记在旧活动上。若 timectl 报告该段已超出撤销窗口、来源不是 agent、或起点不符，说明它不是你刚写的那条，须先与用户确认再用 `delete --id`。
- 不用反向记录伪装撤销；v1 没有恢复接口，误删需按原信息重新写入并重新通过全部校验。
- 空白使用 `gaps --date`；明细使用 `segments --from --to`；需要服务端汇总口径时用 `request GET "/v1/time/summary/range?from=&to="`。用户只问汇总时不主动展开完整明细。
- 时间域的撤销只影响 `time.sqlite3`。同一次对话里若还写过账务，那一笔要另用 `finctl void --id ... --reason ...` 单独撤销；一条命令永远只动一本账。

## 9. 错误分级

- 本地写前校验失败（`LifeOSTimeError`）或服务端明确返回 4xx：可以确认未写入；修正输入事实后才提交新请求。
- 5xx、超时、断连或重定向（`LifeOSTransportError`）：提交结果未知，禁止直接重试（原请求可能已落账）；先用只读 `segments` 查询目标窗口，再根据账本事实决定是否仍需写入。
- `reconcile` 已返回成功 transaction、但随后的验证 GET 失败：事务已经提交，回执带 `verificationStatus: failed_after_commit`；禁止重放计划，稍后只做只读核验。
- 401：停止，提示检查本机连接配置或恢复原服务，不索要用户把 Token 发到聊天。
- 422：按机器码处理。`unknown_category/unknown_project` 展示 valid；`category_nature_mismatch` 必须改选同 nature 分类；`overlap` 展示 conflicts 并建议修边；`auto_close_would_invert` 引导先修正或撤销旧段；时间/扣除错误只追问对应事实；`missing_user_confirmation` 回到明确确认步骤。
- 404：重新读取 segments/configuration 确认目标，不猜 ID。
- 路径写成 `/v1/fin/*`：lifeconn 在发包前就会拒绝（域前缀白名单），这不是服务端故障，而是提醒你这句话属于财务域——换 finctl 重写那一笔。

## 10. 十条模拟对话走查

1. 现在开始写代码 → `switch --now` → 原样转达 `display`。
2. “先记到这儿，我不记了” → `stop --now`（进行中段由 timectl 定位）→ `display` 下行是 `⏸ … 起不再记录`，账本留白已在其中，不必另说。注意“干完了”后面通常还有下一件事，那属于走查 3。
3. 接下来开会 → `switch --now`，核对回执 `seamless: true` 与 `closedPrevious` → 原样转达 `display`。**不得写成 stop 加 record。**
4. 刚才开会一个半小时 → 先反问几点开始或到几点结束，拿到钟点后 `record`。禁止自己倒推 90 分钟。
5. 上午九点到十一点写文章 → `record --start 9:00 --end 11:00`。
6. 中间刷手机半小时 → reconcile 原子拆段并写后核验；事务不可用时才走三步降级。
7. 我去睡了 / 我起来了 → 睡眠与起床后的活动都是能命名的事，一律 `switch`；“昨晚 12 点睡”按补录处理。
8. 今天或这周投入多少 → `summary/range`，只返回所问数字。
9. 1:12 入睡、5:16 醒来、刷手机到 7:23、现在查看枫叶银行开户文件且非核心 → 计划落地为 JSON 文件后一次 reconcile，得到睡眠 01:12–05:16、刷手机 05:16–07:23、运营事务/support 07:23 起；写后确认无额外 1 分钟段。
10. 上海时间 2026-08-01 07:01，用户说“0 点到 6:50 睡觉，零点前刷手机，6:50 到现在并接下来继续刷手机”，随后强调“已经是 1 号” → 作废任何 7 月 31 日凌晨计划；重新 clock 后所有写命令带 `--today 2026-08-01`；冻结为 1 日 00:00–06:50 睡眠、1 日 06:50 起单一开放“刷手机”段，7 月 31 日只保留“零点前”待确定的部分；先查询跨日 open segment，再用一次 reconcile 对账，不在 07:01 制造同活动边界。
11. 23:50 说“我刚从剪视频换成休息了，23:45 换的” → `switch --title 休息 --category 休息 --at 23:45`；日期由 timectl 判定，不要自己拼日期。
12. 08:00 说“昨晚 23:18 睡的，6:50 起来的”（补录已结束的跨零点睡眠）→ `record --start 23:18 --end 6:50`：得到一条从前一日 23:18 跨到当日 06:50 的记录，不拆成两段，也不需要自己判断哪个钟点属于哪一天。
13. 刚 `switch` 到“午餐”，用户立刻说“我没说吃饭，还在写代码” → `cancel --expect-start <该次回执的 boundary>`：误开的午餐被软删，被它收尾的“写代码”在同一事务里恢复为进行中。回执 `restoredPrevious` 里的时段 ID 是新的，后续引用这段必须用新 ID；账本不留任何 1 分钟垃圾，也不留被截断的开发段。
14. 用户 09:00 说“先停一下”，10:30 才说“接下来开会” → 直接 `switch --now` 会被拒绝：空白 90 分钟远超 5 分钟自动对齐上限，timectl 要求先问清那段时间在做什么（见第 4 节）。若用户答“那段不记”，才用 `switch --now --allow-gap`；回执给出 `openedWithoutPredecessor`、`boundary` 与 `precedingRecord`，`display` 上行为 `⚠ 未记录 · 09:00–10:30 · 1h30m（已确认不记）`，原样转达即可，不要改写成一次无缝切换。若用户答出了那段在做什么，就先 `record --start 9:00 --end 10:30` 把它补上，再 `switch`。
15. “前天上午 9 点到 11 点开了个会” → `record --days-ago 2 --start 9:00 --end 11:00`。不要把它写成 `--start 9:00`（会落到今天），也不要自己算出前天的日期。
16. 上一步误用执行时刻把“接电话”收在 09:43，用户接着说“9:44 弄枫叶银行的资料” → 一条 `switch --title "弄枫叶银行的资料" --category 运营事务 --nature support --at 9:44`。timectl 会把“接电话”的结束对齐到 09:44 并在回执给出 `alignedPrevious`；`display` 为 `✓ 接电话 · 09:31–09:44 · 13m（已由 09:43 对齐到 09:44）` 与 `▶ 弄枫叶银行的资料 · 09:44 起`。绝不留下 09:43–09:44 的空白。
17. “刚花 38 块吃了午饭，现在开始写代码” → 这是混合句，拆两笔：`switch --title "写代码" --now --today ...` 走时间账本，午饭那 38 元另用 `finctl expense` 走财务账本；两条回执各自逐行原样转达，绝不合并成一行，时间行里不出现 `¥`。
